## 一、更新三步（每次都按这个顺序）

在 `content_dashboard` 目录下执行：

```bash
# 1. 改数据：只改 data/dashboard.json（UTF-8 编码，标准 JSON，不能写注释，最后一项后面不能有逗号）
#    改完把 updated_at 改成当前北京时间，updated_by 写清楚是谁、依据哪次快照

# 2. 校验：必须看到「✓ 校验通过」
python3 validate.py
#    Windows 上如果没有 python3 命令，用：python validate.py
#    出现「✗ 校验失败」时，按提示的路径（例如 $.topics[0].snapshots[2].slot）改，再跑一次，直到通过

# 3. 生成页面
python3 build.py
#    输出 dist/index.html；页面右上角显示「数据更新于 …（北京时间）」= updated_at
```

- 校验不过时 `build.py` 会拒绝生成，旧的 `dist/index.html` 保持不变。
- `build.py` 生成后会再扫一遍整页文字（红线词、隐私信息、外部资源），有问题同样会失败。
- 需要 Python 3.8 以上，不用装任何第三方包。页面代码在 `build.py`（原有部分）和 `cockpit.py`（驾驶舱、获客、五平台对比）。
- 想先在副本上试：`python3 validate.py 路径/副本.json`（`build.py` 固定读 `data/dashboard.json`）。

## 二、三条铁律

1. **不编数字。** 没拿到的数据写 `"待采集"`；后台打不开、平台不给的写 `"拿不到"`。页面会显示成灰色标签。
2. **不写红线词，连引用、描述违规内容时也不写。** 词表以 `validate.py` 里的 `RED_WORDS` 为准，命中就失败；其中的英文词不区分大小写。要记录违规，只写「描述」，例如：
   - ✅ `"评论区出现违规广告类评论，待 Jason 本人处理"`
   - ✅ `"正文仍含红线词，待改"`
   - ❌ 把评论原文或违规词抄进来
3. **不放隐私和经营数据。** 不写客户名字、微信号或微信 ID、手机号、身份证号，也不写收款、成交额、销售额、订单号、台账。校验器会扫这些模式，命中就失败。看板只放内容和平台公开数据。
   - 获客区块**只允许存每日成交客户数**（`acquisition.deals_daily`），不存成交金额。任何金额类字段（`amount`、金额、价格、收入等）校验直接失败。
   - **大管家和第二大脑都不读取任何销售数据**（不读 CloudBase 账本，不读销售看板的本地数据文件）。成交客户数只抄销售看板Bot 或章鱼哥给的数字。

## 四、`kpis`（顶栏 KPI）

```json
{"key": "above_median", "title": "破中位数", "value": null, "unit": "条", "status": "pending",
 "note": "本周首条（抖音第88集）2 小时快照约 11:44"}
```

| 字段 | 说明 |
|---|---|
| `key` | 固定标识：`collect` 采集条数、`topics` 选题数、`published` 发布数、`above_median` 破中位数、`mechanism` 机制验证进度 |
| `title` | 卡片标题 |
| `value` | 数字或文字（如 `"1 / 10"`）。**`status` 为 `pending` 时必须是 `null`**，页面显示「待采集」 |
| `unit` | 单位，可为空字符串 |
| `status` | `real` 有真实数据 / `pending` 待采集 |
| `note` | 卡片下方的小字说明，写清楚数据怎么来的 |
| `source` | 选填（1.1）：数据来源，例 `"2 小时快照 vs 中位数基线"`；页面显示「来源：…」 |
| `time` | 选填（1.1）：采集时间 `YYYY-MM-DD HH:MM`；不写就用 `updated_at` |
| `prev_value` | 选填（1.1）：上周同口径数值，数字或 `null`；`null` 显示「上周待录入」，有数字才显示涨跌箭头。**不知道就写 null，别估** |
| `result` | 选填（1.1）：`true` = 结果指标。目前驾驶舱 4 张结果卡 = `published` 发布数、`above_median` 破中位数 ＋ 本周成交客户、加微→成交转化率（后两张由 `acquisition.daily` 和 `deals_daily` 自动算） |

原来 5 张 KPI 卡挪到页面下方「过程指标」，内容不变。

本周统计口径：本周一 00:00 到现在（北京时间）。「破中位数」= 本周发布作品中，抖音互动和（赞＋藏＋转）超过 `baselines.抖音.median` 的条数（视频号同理）。有了第一个 2 小时快照后，把 `status` 改成 `real`，再填 `value`。

## 五、`accounts`（账号总览条）

```json
{"platform": "抖音", "time": "2026-10-19 10:20",
 "metrics": {"粉丝": 2361, "关注": 2255, "获赞": "3.2万", "作品": 97},
 "note": "粉丝较昨日 -1（2362→2361）"}
```

- `platform` 只能是：`抖音`、`视频号`、`公众号`、`小红书`、`朋友圈`
- `metrics` 的值可以是数字，也可以是平台原样显示的文字（如 `"3.2万"`）
- 每次快照直接覆盖该平台这一项，不用保留历史，历史在作品追踪总表里

## 七、`collection`（采集入口卡片）

```json
{"name": "痛点第12批", "count": "19 条", "detail": "小红书 9 · 抖音 2 · 知乎 8；剔除重复 1 条", "time": "10-19 07:11"}
```

四个字段都是文字，都必填。新的一批来了就替换最旧的那张卡片，建议保持 5 张。

**明细（第二轮新增，选填）：** 每张卡片可以加 `items`（点卡片弹出明细列表）和 `items_source`（明细取自哪个文件）。没有 `items` 或写 `[]` 时，弹层显示「明细待大管家补充」。

```json
{"name": "痛点第12批", "count": "19 条", "detail": "…", "time": "10-19 07:11",
 "items_source": "painpoint_research/2026-10-19_batch12.md",
 "items": [
   {"title": "Skill 装好了但用不起来（登录失败、找不到权限选项、不会改 Skill）", "platform": "小红书",
    "time": "10-19 07:11", "note": "原帖：用了这么久 Codex，原来 Skill 还能这样装？", "url": "https://www.xiaohongshu.com/explore/…"}
 ]}
```

| 字段 | 必填 | 说明 |
|---|---|---|
| `title` | 是 | 痛点：写痛点原文或摘要（用批次文件里的「痛点标签」）；对标账号：账号名；痛点词：词本身 |
| `platform` | 否 | `小红书`、`抖音`、`知乎`、`X`、`视频号`、`公众号`、`其他` |
| `time` | 否 | 采集时间（批次开始时间即可） |
| `note` | 否 | 补充：原帖标题、作者和互动数、对标账号的「代表作品：…」 |
| `url` | 否 | 必须 `https://` 开头 |
| `count` | 否 | 只给痛点词用：出现次数（≥0 整数） |

- **不收评论者昵称、地区等个人信息**，只收帖子和公开账号。
- 原文含红线词的条目，`title`（必要时连 `note`）整条换成「涉及敏感词，已隐去」，保证校验 0 命中。
- 第二轮的明细由 `_build/extract_collection_items.py` 从大管家的原始文件只读抽取：痛点第12批、第11批 ← `painpoint_research/2026-10-19_batch12.md`、`batch11.md`；今日热门 ← `social_hot_2026-10-19/final_report.md`；对标账号 ← `benchmark/候选名单_抖音头部.csv`、`候选名单_抖音低粉爆帖线索.csv`。「痛点池累计」目前没有词频文件，`items` 为空。

## 八、`topics`（选题流水线）

### 8.1 一个选题的完整结构

```json
{
  "id": "2026-10-19-lunwen",
  "date": "2026-10-19",
  "title": "写论文用 Claude 还是 ChatGPT？按 5 个阶段给你答案",
  "stage": 5,
  "stage_note": "5 个平台已发布；首个快照已采，线上红线复查待做",
  "source": "小红书「学术论文修改如何求助ai」…",
  "mechanism": "第 8 条 科研流程 ＋ 第 5 条 清单",
  "owners": "大管家统筹 · 分 Bot 出各平台版 · 第二大脑二审",
  "flags": ["focus"],
  "platforms": [ … ],
  "snapshots": [ … ],
  "compare": "待采集（等 2 小时快照）",
  "redline": {"level": "todo", "note": "发布后线上复查待做"},
  "blockers": ["发布后线上红线复查未做"]
}
```

| 字段 | 类型 | 说明 |
|---|---|---|
| `id` | 文字 | 唯一，只用小写字母、数字、短横线，建议 `日期-拼音简称` |
| `date` | 文字 | 计划或实际发布日 `YYYY-MM-DD` |
| `title` | 文字 | 选题标题 |
| `stage` | 整数 1–7 | 当前环节：1 采集、2 选题、3 蒸馏二创、4 审核交付、5 发布与线上复查、6 数据反馈、7 复盘调整 |
| `stage_note` | 文字 | 一句话现状，例 `"7 天跟踪中（第 3 天）"` |
| `source` / `mechanism` / `owners` | 文字 | 来源、对应机制条目、负责分工 |
| `flags` | 列表 | 可为空 `[]`；可选 `focus` 今日重点（卡片高亮）、`best` 本周最佳、`worst` 本周最差 |
| `platforms` | 列表 | 各平台状态，见 8.2 |
| `snapshots` | 列表 | 数据快照，见 8.3；没发布就写 `[]` |
| `compare` | 文字 | 和中位数对比的结论，例 `"抖音 87 ＞ 中位 50.5（未到 2 倍线 101）"`；没数据写 `"待采集"` |
| `redline` | 对象 | `level`：`pass` 通过 / `check` 待核 / `hit` 命中 / `todo` 复查待做；`note`：说明（只描述，不写原词） |
| `blockers` | 列表 | 卡点，每条一句话；没有就写 `[]`，页面显示「卡点：无」 |

页面排序：环节 5、4、3 在最上面，然后是 6、7，最后是 1–2 的备选题。

### 8.2 `platforms`

```json
{"platform": "抖音", "status": "published", "time": "10-19 09:44", "work": "第88集",
 "url": "https://www.douyin.com/note/7698188943593920889"}
```

| 字段 | 必填 | 说明 |
|---|---|---|
| `platform` | 是 | 抖音 / 视频号 / 公众号 / 小红书 / 朋友圈 |
| `status` | 是 | `published` 已发布、`made` 已制作未发布、`pending` 状态待采集、`paused` 停更中、`none` 不做、`tbd` 待定 |
| `time` | 否 | 发布时间，`MM-DD HH:MM`。已发布但不知道时间时，不写 `time`，在 `note` 里写 `"发布时间待采集"` |
| `work` | 否 | 作品编号，如 `"第88集"` |
| `url` | 否 | 作品链接，必须 `https://` 开头 |
| `note` | 否 | 补充说明，显示在平台标签下方 |

### 8.3 `snapshots`（加一条快照）

```json
{"slot": "2h", "platform": "抖音", "time": "2026-10-19 11:46", "elapsed": "约 2 小时",
 "metrics": {"赞": 3, "评": 0, "藏": 2, "转": 1, "互动和": 6}, "note": ""}
```

**slot 怎么选：**

| slot | 用在什么时候 | 页面格子 |
|---|---|---|
| `2h` | 发布后约 2 小时那次 | 2 小时 |
| `15:00` | 发布当天 15:00 左右那次 | 15:00 |
| `21:00` | 发布当天 21:00 左右那次（21:18 这种也算） | 21:00 |
| `24h` | 发布后约 24 小时（次日上午那次） | 24 小时 |
| `72h`、`other` | **旧标签，仍能读，新快照不要再用。** `other` 会按采集时间自动归入上面 4 个时段之一（规则见下）；`72h` 和归不进去的留在数据里，页面图表不显示，只在卡片「展开 → 全部快照」里列出 | — |

**页面 4 个时段（第二轮）：** 2 小时、下午 3 点、晚上 9 点、24 小时。已标 `2h` / `15:00` / `21:00` / `24h` 的直接用；标 `other` 的按采集时间自动归：距发布 1.5–3 小时 → 2 小时；发布当天 14:00–17:30 → 下午 3 点；发布当天 19:00 以后 → 晚上 9 点；距发布 20–30 小时 → 24 小时。同一时段有多条时，优先已标好的，其次离目标时间最近的。距发布的时间按 `platforms[].time` 算，没有发布时间就只认已标好的。

**选题卡片图表：** 只画抖音、公众号、视频号、小红书 4 个平台（朋友圈只在发布状态里显示 ✓/✗）。每个平台 4 根堆叠柱，赞、评、藏、转 4 种颜色，柱高 = 这 4 项之和（**图上的「互动合计」含评论，和基线口径的 `互动和` 不完全一样**，对比中位数仍看 `互动和`）；折线连起各时段的合计。平台没有的字段（例如视频号没有 `藏`）按缺失处理，不当 0，图上标「无藏字段」。

- `time`：实际采集时间（北京时间）`YYYY-MM-DD HH:MM`；`elapsed`：距发布多久，例 `"约 35 分钟"`、`"约 23 小时"`。
- `time`：实际采集时间（北京时间）`YYYY-MM-DD HH:MM`；`elapsed`：距发布多久，例 `"约 35 分钟"`、`"约 23 小时"`。
- **只追加，不删旧快照。** 每次快照给每个已发布平台各加一条。

**指标名（metrics 的键）统一用这些：**

| 指标名 | 含义 | 常用平台 |
|---|---|---|
| `播放` | 播放量 | 视频号、抖音 |
| `阅读` | 阅读数 | 公众号 |
| `赞` | 点赞 / 喜欢 | 全部 |
| `评` | 评论数 | 全部 |
| `藏` | 收藏数 | 抖音、小红书 |
| `转` | 转发 / 分享 | 全部 |
| `在看` | 在看 | 公众号 |
| `关注` | 这条带来的新关注 | 视频号 |
| `互动和` | 抖音 = 赞＋藏＋转；视频号 = 喜欢＋转发＋点赞（与基线口径一致） | 抖音、视频号 |

四平台对比表的主指标：抖音看 `互动和`，视频号看 `播放`，公众号看 `阅读`，小红书看 `互动和`。

**缺数据怎么写：**

- 某个指标没拿到：`"评": "待采集"`
- 平台后台进不去（例如助手登录过期）：整条写 `"metrics": "拿不到"`，`note` 写原因，例 `"视频号助手登录过期，待扫码"`
- 值只能是数字、`"待采集"`、`"拿不到"`；写别的文字会校验失败

### 8.4 移动环节

改 `stage` 和 `stage_note`，必要时同步改 `platforms[].status`、`redline`、`blockers`。参考：

- 拍板 → `stage` 2 改成 3
- 各平台版交付、二审中 → 4
- 章鱼哥发了第一个平台 → 5（加 `time`、`work`、`url`，把 `redline.level` 设为 `todo`）
- 线上复查完、开始收快照 → 6（`redline.level` 改成 `pass` / `check` / `hit`）
- 7 天跟踪结束、周复盘写完结论 → 7

同时更新顶栏 `kpis` 里的 `topics`、`published`，以及 `flags`（`focus` 每天只给一个选题）。

## 九、`mechanisms`（爆款文案机制）

```json
{"updated": "2026-10-19 周复盘", "hypotheses_count": 8,
 "items": [{"no": 3, "title": "价格、额度类能拿曝光但互动差，此类题暂停", "status": "初步验证"}]}
```

`status` 只能是：`待验证`、`初步验证`、`已验证`、`暂停`、`未标注`。`no` 不能重复。以 `content_playbook/爆款文案机制.md` 为准同步。改了以后记得同步 `kpis` 里 `mechanism` 的 `value`。

## 十、校验器会拦下什么

- 缺字段、类型不对、取值不在上面的枚举里
- 日期或时间格式不对（`YYYY-MM-DD`、`YYYY-MM-DD HH:MM`）
- `stages` 不是正好 1–7
- KPI 为 `pending` 但 `value` 不是 `null`
- 快照指标里出现非数字文字（`待采集`、`拿不到` 除外）
- 链接不是 `https://`
- **任何文字里**（包括字段名）出现红线词
- 疑似微信号或微信 ID、手机号、身份证号、客户名单、台账或收款类字样
- （1.1）获客区块：渠道不在 4 个之内、`daily` 填了渠道拆分但 4 个渠道合计 ≠ 当天总数（小于、大于都报错；渠道全空可以通过）、`deals_daily` 渠道合计大于成交客户数、同一天重复、出现名字/昵称/微信/手机/订单类字段、`deals_daily` 多出成交客户数以外的字段、`provided_by` 不是「销售看板Bot」或「章鱼哥」、月目标不是数字或 null
- （1.1）整份 JSON 里任何金额类字段名（`amount`、`price`、`revenue`、金额、价格、收入、成交额等）
- （1.1）拍板区超过 3 条；`topic_id` 指向不存在的选题
- （1.1）任何采集时间晚于现在 10 分钟以上（多半是日期写错）
- （1.1）`wechat_leads.csv` 表头不对、渠道不认识、人数不是整数
- （第二轮）`collection[].items` 字段不认识、链接不是 `https://`、`count` 不是整数；明细文字同样做红线和隐私扫描

出错时会逐条列出位置，退出码为 1；全部通过退出码为 0。超过 24 小时的数据只提醒，不拦构建（见第十四节）。

## 十二、`acquisition`（私域获客 · 北极星指标）

内容生产板块最终看获客：**本周私域新增微信好友** 是北极星，放在驾驶舱最顶上。只存**人数和来源**，不存名字、头像、微信号、聊天内容。

```json
"acquisition": {
  "north_star": "本周私域新增微信好友",
  "adds_source": "章鱼哥每晚报数（第二大脑每晚 21:30 提醒）",
  "deal_source": "销售看板成交客户数（同步方式待章鱼哥拍板）",
  "deal_provider": "销售看板Bot 只读统计或章鱼哥报数，只给每日成交客户数",
  "sources": [
    {"key": "抖音", "label": "抖音", "path": "主号 @ 小号「章鱼哥AI助手」，懂的人从小号加微信", "status": "active"},
    {"key": "视频号", "label": "视频号", "path": "看完后在微信生态里直接联系或加微信", "status": "active"},
    {"key": "公众号", "label": "公众号", "path": "读完后在微信生态里直接联系或加微信", "status": "active"},
    {"key": "小红书", "label": "小红书", "path": "后续再做，届时先定合规方案", "status": "not_started"},
    （第二轮起只有上面 4 个渠道）
  ],
  "monthly_target": {"wechat_adds": null, "new_customers": null},
  "funnel_inputs": {
    "exposure": {"value": null, "source": "各平台本周播放、阅读、观看合计（大管家汇总）", "time": null},
    "visits":   {"value": null, "source": "抖音小号主页访问 ＋ 微信内问询（大管家汇总）", "time": null}
  },
  "daily": [],
  "deals_daily": []
}
```

| 字段 | 说明 |
|---|---|
| `north_star` / `adds_source` / `deal_provider` | 页面上的标题和来源说明，一般不改 |
| `deal_source` | **固定 `"销售看板成交客户数（同步方式待章鱼哥拍板）"`**，写别的校验失败 |
| `sources` | 4 个渠道，`key` 固定为 `抖音`、`视频号`、`公众号`、`小红书`（第二轮删掉了朋友圈和来源未知）；`status`：`active` 在做 / `not_started` 暂未做获客（页面灰显并打标签）。小红书目前是 `not_started` |
| `monthly_target` | 月目标：加微人数 `wechat_adds`、成交客户数 `new_customers`（不设金额目标）。**没定就写 `null`，页面显示「待定」**，进度条为空。章鱼哥定了再填 |
| `funnel_inputs` | 漏斗上两层（本周内容曝光、小号主页访问/问询），整数或 `null`。有数字时必须写 `time`。`null` 显示「待录入」 |
| `daily` | 每日加微记录，见 12.1 |
| `deals_daily` | 每日成交汇总，见 12.2 |

**页面怎么算（全部自动，不用手算）：**

- 本周加微 = `daily` 里本周（`week.start`～`week.end`）各天 `count` 相加；上周 = 再往前 7 天；本月累计 = 本月 1 日到今天。**一天都没报时显示「待录入」，不是 0。**
- 漏斗：内容曝光 → 小号主页访问/问询 → 加微 → 成交（本周成交客户数），相邻两层都有数字才算转化率，否则显示「—」。
- 获客来源榜 = 本周各天 `sources` 按渠道相加；「按内容」= 本周各天 `by_content` 相加。
- **口径（10-19 16:18）：** 某天只要填了渠道，4 个渠道之和必须正好等于当天 `count`；说不清渠道的那天，整项不写 `sources`（= 渠道未填），只计入总数。**没有「未分渠道」这一项。**
- 结果 KPI「本周成交客户」= 本周 `deals_daily` 相加；「加微→成交转化率」= 本周成交客户 ÷ 本周加微，两项都有数字才算，否则显示「待录入」；都和上周比（转化率按百分点比）。

### 12.1 `daily`（每日加微 · 章鱼哥每晚报数）

**更新方式：** 第二大脑每晚 21:30 提醒章鱼哥报「今天加微 X 人，来自 XX」，收到后加一条。当天没加人也记一条 `count: 0`；**没报数的那天不要建记录**（页面才能区分「0 人」和「待录入」）。

```json
{"date": "2026-10-19", "count": 4,
 "sources": {"抖音": 3, "公众号": 1},
 "by_content": [{"label": "抖音第88集", "topic_id": "2026-10-19-lunwen", "count": 2}],
 "note": "", "reported_at": "2026-10-19 22:05", "reported_by": "章鱼哥报数"}
```

| 字段 | 必填 | 说明 |
|---|---|---|
| `date` | 是 | `YYYY-MM-DD`，同一天只能一条 |
| `count` | 是 | 当天新增微信好友数，≥0 整数 |
| `sources` | 否 | 渠道拆分，键只能是 4 个渠道之一。**可以不写或写 `{}`（= 渠道未填）**；只要写了，**4 个渠道合计必须正好等于 `count`**，小于或大于都校验失败。没做的渠道写 0 或不写都行 |
| `by_content` | 否 | 能对应到具体内容时填：`label` 作品名或编号，`topic_id` 选填（必须是 `topics` 里有的 id），`count` 人数；合计不能超过 `count` |
| `note` | 否 | 最多 60 字，只写来源情况，**不写人** |
| `reported_at` | 是 | 记录时间 `YYYY-MM-DD HH:MM` |
| `reported_by` | 是 | 例 `"章鱼哥报数"` |

### 12.2 `deals_daily`（每日成交客户数）

**数据源是「销售看板成交客户数」，按天记录，同步方式待章鱼哥拍板。** 只记当天成交客户数（可选来源），由 **销售看板Bot** 只读统计后提供，或由 **章鱼哥** 直接报。**不记成交金额。** 大管家和第二大脑**都不读取任何销售数据**，也不改销售看板里的任何东西。

```json
{"date": "2026-10-19", "new_customers": 1,
 "sources": {"抖音": 1},
 "provided_at": "2026-10-19 21:30", "provided_by": "销售看板Bot"}
```

| 字段 | 必填 | 说明 |
|---|---|---|
| `date` | 是 | `YYYY-MM-DD`，同一天只能一条 |
| `new_customers` | 是 | 当天成交客户数，≥0 整数 |
| `sources` | 否 | 可选渠道拆分（键同 4 个渠道），合计不能大于 `new_customers` |
| `provided_at` | 是 | 提供时间 `YYYY-MM-DD HH:MM` |
| `provided_by` | 是 | **只能是 `"销售看板Bot"` 或 `"章鱼哥"`** |
| `note` | 否 | 最多 60 字 |

只允许上面这些字段，多写（例如金额、明细、客户、订单）校验直接失败。本周、本月合计由页面自动算。

### 12.3 可选：`data/wechat_leads.csv`

不想改 JSON 时，也可以把加微数逐行写进这个 CSV（UTF-8，表头固定）：

```csv
date,count,source,note
2026-10-19,3,抖音,
2026-10-19,1,公众号,
```

- 一行 = 某天某个渠道的人数；同一天多行会合并成一条 `daily` 记录。`source` 只能是 4 个渠道之一，或留空 = 只计入当天总数（渠道未填）。同一天如果既有留空行又有渠道行，渠道合计就会小于总数，校验会报错：要么全部写渠道，要么全部留空。
- `build.py` / `validate.py` 发现文件就合并（只在内存里合并，**不会改写 dashboard.json**），没有文件就跳过。
- 同一天 JSON 和 CSV 都有时，**以 JSON 为准**，CSV 那天跳过并给出提醒。
- CSV 的「记录时间」取文件修改时间。

## 十四、新鲜度（每个数字都标来源和采集时间）

- 页面上每个数字下面都有「来源：… · 采集 MM-DD HH:MM」。

## 十五、页面上手填加微（第二轮）

页面是静态的，没有后端。章鱼哥在页面上填的数字**只存在他自己这台设备的浏览器里**（localStorage，键名 `content-board-acq-v1`），要变成正式数据得走同步口令。

**能填的地方**

- 北极星卡片：周一到周日 7 个小格，填当天新增微信好友总数。今天高亮，未来的日子置灰不能填。
- 获客来源榜：选日期（默认今天），每个渠道一个数字框，带 −/+。

**怎么算**

- 每天的总数：填了总数就用总数；只填了渠道没填总数，总数 = 渠道合计。
- 只填总数、4 个渠道全空也有效（口令写「渠道未填」）。
- 填了渠道，4 个渠道合计必须正好等于总数。不相等（小于或大于）时，当天那行、渠道数字框、北极星对应那一格都标红，提示「渠道合计 X，不符」。
- 本机填的数字和正式数据（`acquisition.daily`）合并显示：
  - 某天正式数据里没有 → 用本机数字，标「未同步」，北极星合计旁边标「含未同步」。
  - 某天正式数据里已有 → 以正式数据为准，本机那天标「已同步」，**不重复计算**。
  - 例外：本机那天的修改时间晚于正式数据的 `reported_at`，而且数字不一样 → 当成待同步的更正，**替代**当天（不叠加），标「未同步」。
- 北极星合计、本月累计、漏斗「加微」层、「加微→成交转化率」都按合并后的数字算。

**同步口令**

点「复制同步口令」，生成并复制所有「未同步」的天（没有未同步的，就生成当前选中那天），一天一行，例如：

```
加微 10-19：共 5 人；抖音 3，视频号 1，公众号 1，小红书 0
加微 10-20：共 2 人；渠道未填
```

只要有一天渠道合计不符，**不能复制**：口令框里那天写「渠道合计不符」，下方提示「10-19 渠道合计不符，改对再复制」。改对了再点一次。

章鱼哥把这段发给第二大脑，第二大脑据此在 `acquisition.daily` 里写（或更新）当天记录：`count` = 共 X 人，`sources` 写口令里的 4 个渠道（合计等于共 X 人；「渠道未填」就不写 `sources`），`reported_by` 写「章鱼哥页面口令」，`reported_at` 写写入时间。重新构建发布后，页面上这些天自动变成「已同步」。
